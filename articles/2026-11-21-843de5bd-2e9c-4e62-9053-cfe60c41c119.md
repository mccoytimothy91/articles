# 用 traceId 串联运单的跨服务调用

<!-- content-workspace-job:843de5bd-2e9c-4e62-9053-cfe60c41c119 -->

## 问题场景

运单的一次请求经过网关、订单、库存三个服务，出问题后要在三个服务的日志里按时间戳人工对齐，一条链路查半小时。

## 实现步骤

网关入口检查是否已有 traceId，没有就生成一个。

```java
String tid = req.getHeader("X-Trace-Id");
if (tid == null || tid.isBlank()) {
    tid = UUID.randomUUID().toString();
}
MDC.put("traceId", tid);
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
```

放进 MDC，日志模板统一输出，排查时按 id 一搜就能拉出整条链路。

```java
logger.info("trace={} path={}", MDC.get("traceId"), req.getRequestURI());
```

调用下游时放进请求头透传，形成完整链路。

```java
httpReq.header("X-Trace-Id", MDC.get("traceId"));
```

## 注意事项

异步线程不会继承 MDC，提交任务时要手动传递；traceId 要防止被外部伪造，入口处对格式做校验。

在资源受限的环境下，要避免在高峰期执行这类操作，保证每一步都可验证。

从长期维护角度看，先把最小可复现的用例固定下来，让容量规划更有依据。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。

在多人协作的项目里，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。
