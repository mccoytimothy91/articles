## 问题场景

工时单导出要拉取多个分片再合并成一份文件，串行执行时总耗时随分片数线性增长。

## 实现步骤

按分片编号构造任务，提交到固定大小的线程池，池大小取分片数与 CPU 核数的折中。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def pull(part):
    rows = load_part("timesheet", part)
    return part, len(rows), rows
```

每个任务只负责自己那段数据并返回结果对象，主线程用 as_completed 按完成顺序收集。

```python
def export(parts, workers=6):
    out = {}
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futs = {pool.submit(pull, p): p for p in parts}
        for f in as_completed(futs):
            part, n, rows = f.result()
```

## 验证方法

## 注意事项

线程池不适合 CPU 密集逻辑，GIL 会让加速比趋近于 1；任务里不要直接写同一个文件句柄，交回主线程统一写。

在跨团队协作时，要避免在高峰期执行这类操作，保证每一步都可验证。

针对这类偶发问题，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，让排查路径更短。

如果数据量继续增长，优先用工具把现状量化出来再动手，让容量规划更有依据。

从成本角度看，应当限定作用范围避免影响其他业务，使整体改动风险可控。
