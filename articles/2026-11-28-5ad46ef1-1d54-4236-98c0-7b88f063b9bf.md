# 通知组件的行为用轻量 DOM 测试固定下来

<!-- content-workspace-job:5ad46ef1-1d54-4236-98c0-7b88f063b9bf -->

## 问题场景

通知组件改一次样式就担心逻辑被带坏，手工点页面回归又太慢。

## 实现步骤

用 jsdom 造一个最小文档环境，把组件挂到容器上。

```javascript
import { JSDOM } from 'jsdom';
const dom = new JSDOM('<!doctype html><div id="root"></div>');
global.document = dom.window.document;
```

断言渲染出的文本、类名与事件后的状态变化，不断言具体标签结构。

```javascript
export function mount(html) {
  const root = document.querySelector('#root');
  root.innerHTML = html;
  return root;
}
```

每个用例结束后清空容器，避免上一个用例的节点影响选择器。

```javascript
const root = mount('<p class="notice">通知</p>');
console.assert(root.querySelector('.notice').textContent === '通知', 'render');
console.log('cases', 1, root.children.length, 9);
```

## 注意事项

jsdom 不执行真实布局，依赖尺寸的断言要改用桩值；异步渲染要用 await 或宏任务等待后再断言。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

针对这类偶发问题，尽量把决策依据写进变更说明，便于横向对比不同方案的效果。

从长期维护角度看，先把最小可复现的用例固定下来，以便后续复盘有据可查。

遇到复杂链路时，先把最小可复现的用例固定下来，让排查路径更短。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

针对这类偶发问题，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

上线初期，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。
