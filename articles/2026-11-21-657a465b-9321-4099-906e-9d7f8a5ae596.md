# 用 SSE 向消息页面推送实时状态

<!-- content-workspace-job:657a465b-9321-4099-906e-9d7f8a5ae596 -->

## 问题场景

消息的进度页面用轮询，每秒一次，几百个用户同时打开就把接口打满，大部分请求还没有新数据。

## 实现步骤

服务端保持长连接，响应头声明事件流类型并关闭缓存。

```typescript
res.writeHead(200, {
  "Content-Type": "text/event-stream",
  "Cache-Control": "no-cache",
  Connection: "keep-alive",
});
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

有新数据就往连接里写一条事件，格式是 data 加空行。

```typescript
const timer = setInterval(() => {
  res.write(`data: ${JSON.stringify({ t: Date.now() })}\n\n`);
}, 1000);
```

客户端断开时清理定时器，否则连接关了还在往里写，服务端句柄泄漏。

```typescript
req.on("close", () => {
  clearInterval(timer);
  res.end();
});
```

## 注意事项

SSE 只支持服务端到客户端单向通信，需要双向就用 WebSocket；中间代理可能缓冲响应，要显式关闭缓冲并调大超时。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

在跨团队协作时，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。
