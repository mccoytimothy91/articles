# 用令牌桶给传感器接口做限流

<!-- content-workspace-job:109b6891-68ee-46f0-bc67-8a6fced7f4ed -->

## 问题场景

传感器的开放接口被合作方在整点集中调用，瞬时流量是平时的二十倍，下游直接被压垮。简单的固定窗口计数又会在窗口边界放过两倍流量。

## 实现步骤

令牌桶按固定速率补充令牌，桶容量就是允许的突发量。

```go
limiter := rate.NewLimiter(rate.Limit(100), 200)
if !limiter.Allow() {
    http.Error(w, "slow down", http.StatusTooManyRequests)
    return
}
```

按调用方维度分桶，避免一个客户把额度占满影响其他人。

```go
var (
    mu      sync.Mutex
    buckets = map[string]*rate.Limiter{}
)

func of(key string) *rate.Limiter {
    mu.Lock()
    defer mu.Unlock()
    l, ok := buckets[key]
    if !ok {
        l = rate.NewLimiter(rate.Limit(20), 40)
```

## 验证方法

以远超限额的速率压测，通过的请求数应稳定在设定速率附近。

## 注意事项

分桶表的键要设过期，否则海量调用方会把内存撑爆；限流是保护手段，被限流的请求要能快速失败，不能让它继续占用连接。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

针对这类偶发问题，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。
