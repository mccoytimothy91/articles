# 用 saga 编排发票的跨服务事务

<!-- content-workspace-job:94436eaa-be82-4faa-8c86-367fe98052f3 -->

## 问题场景

发票下单要跨订单、库存、支付三个服务，用本地事务包不住。中间某一步失败后，前面已经扣掉的库存没人释放，数据就对不上了。

## 实现步骤

把流程拆成若干本地事务，每一步都实现对应的补偿操作。

```java
try {
    orderService.create(o);
    stockService.lock(o);
    payService.charge(o);
} catch (Exception e) {
    payService.refund(o);
    stockService.unlock(o);
    orderService.cancel(o);
}
// 该片段可重复执行，结果保持不变
```

失败时按逆序执行已成功步骤的补偿，注意补偿本身也可能失败。

```java
void compensate(Runnable step, String key) {
    if (done.add(key)) {
        step.run();
    }
}
```

补偿必须幂等，重复执行不能产生副作用，否则重试会越补越乱。

```java
System.out.println(done.size());
System.out.println(done.contains("refund"));
```

## 验证方法

人为让支付步骤失败，库存应被释放、订单应变为已取消，最终数据一致。

## 注意事项

saga 没有隔离性，中间状态对外可见，需要业务上容忍或用状态机控制；补偿失败要有兜底对账，不能只靠重试。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

在多人协作的项目里，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。
