# 给账户表加缓存时先挡住穿透请求

<!-- content-workspace-job:f04956c3-a8be-4b60-b439-2c5ed2d52e66 -->

## 问题场景

账户表的详情接口被大量不存在的 id 请求，缓存里没有就去查库，查不到又不写缓存，同一个不存在的 id 每秒打几千次数据库。

## 实现步骤

正常结果写缓存并设置过期时间，键名带业务前缀便于清理。

```bash
redis-cli SET accounts:1 '{"id":1}' EX 60 NX
```

空结果也写一个短过期的占位值，挡住重复的穿透请求。

```bash
redis-cli SET accounts:999999 '__nil__' EX 30
redis-cli GET accounts:999999
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
# 上述命令可重复执行，结果幂等
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
```

观察命中率与数据库 QPS，穿透被挡住后 QPS 应大幅下降。

```bash
redis-cli INFO stats | grep -E 'keyspace_hits|keyspace_misses'
```

## 注意事项

空值缓存时间不能太长，否则数据补录后要等过期才可见；更彻底的做法是布隆过滤器或参数合法性校验，把明显非法的 id 直接拦掉。

对于刚接手的同学，要明确各项资源的释放时机，以便快速定位瓶颈。

结合团队现状，可以通过压测确认容量水位，便于横向对比不同方案的效果。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

从长期维护角度看，优先保证失败时能快速定位原因，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。
