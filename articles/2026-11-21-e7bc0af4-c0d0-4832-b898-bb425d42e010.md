# 订单表深分页查询改用延迟关联

<!-- content-workspace-job:e7bc0af4-c0d0-4832-b898-bb425d42e010 -->

## 问题场景

订单表的后台列表翻到几千页时接口直接超时，LIMIT OFFSET 越往后越慢，因为前面那些行虽然不返回，却照样要被读取和丢弃。

## 实现步骤

先用覆盖索引把目标页的主键捞出来，这一步不回表，扫描量可控。

```sql
SELECT id FROM orders WHERE amount > 500 ORDER BY id LIMIT 20 OFFSET 200000;
```

再拿这批主键回表取完整字段，回表次数等于页大小，与偏移量无关。

```sql
SELECT a.* FROM orders a
JOIN (SELECT id FROM orders WHERE amount > 500
      ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

对比两次执行计划，改造后应当只走索引扫描而不是全表扫。

```sql
EXPLAIN ANALYZE
SELECT a.* FROM orders a
JOIN (SELECT id FROM orders ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
```

## 注意事项

延迟关联要求排序字段有序且能被索引覆盖，否则内层仍会 filesort；键集分页（记住上一页最后一个 id）比 OFFSET 更稳，但只支持顺序翻页。

从成本角度看，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

结合团队现状，可以通过日志补充上下文信息，使整体改动风险可控。

在资源受限的环境下，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，避免资源被长期占用。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。
