# 密钥表单在提交前做集中校验并聚焦首个错误

<!-- content-workspace-job:9e5a2aba-1772-4d55-b054-5543e71a2a4f -->

## 问题场景

密钥录入表单有十多个字段，校验分散在提交回调里，用户只看到顶部一个笼统提示。

## 实现步骤

用规则对象描述每个字段的必填、长度与格式要求。

```javascript
const rules = {
  name: (v) => (v.trim().length >= 2 ? '' : '名称至少 2 个字'),
  rotated: (v) => (/^\d+$/.test(v) ? '' : '密钥必须为数字'),
};
```

提交时遍历规则收集错误，把提示挂到对应字段下方。

```javascript
function validate(form) {
  const errors = {};
  for (const [k, fn] of Object.entries(rules)) {
    const msg = fn(form.elements[k].value);
    if (msg) errors[k] = msg;
  }
  return errors;
}
```

## 验证方法

只留一个字段为空提交，应看到该字段提示且光标落在该控件上；全部填对后应正常进入提交分支。

## 注意事项

异步校验要避免竞态，后发的请求可能先返回；聚焦前先确认元素仍然可见，隐藏字段无法获得焦点。

在迁移过程中，可以通过日志补充上下文信息，避免问题积累到难以收场。

从长期维护角度看，先把最小可复现的用例固定下来，降低同类问题再次发生的概率。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

在实际落地时，建议先在小流量环境验证行为是否符合预期，减少不必要的返工成本。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

结合历史事故记录，要把边界条件列成清单逐项确认，降低同类问题再次发生的概率。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，确保线上行为始终可控。
