## 问题场景

统计视频日志里的异常数量时，先把整个文件读成列表再层层过滤，单文件几百兆就吃满内存。

## 实现步骤

第一段逐行读并解析成字典，第二段过滤出目标级别，第三段做计数。

```python
def lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

各段之间用 yield 传递，不构造中间列表，内存占用与文件大小无关。

```python
def parsed(rows):
    for r in rows:
        parts = r.split(" ")
        if len(parts) >= 3:
            yield {"level": parts[1], "msg": " ".join(parts[2:])}
```

每个生成器只做一件事，便于单独替换解析规则或过滤条件。

```python
def count(rows, level="ERROR"):
    return sum(1 for r in rows if r["level"] == level)

print(count(parsed(lines("video.log"))))
# 预期：输出与上文描述一致
```

## 注意事项

生成器只能遍历一次，重复统计要重新构造；异常处理放在最内层，否则一条坏行会中断整条管道。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

如果数据量继续增长，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

上线初期，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。
