## 问题场景

每个用例都重新建一遍理赔单表并插入初始数据，测试跑得慢，且初始化代码复制得到处都是。

## 实现步骤

用 session 级 fixture 建库建表，function 级 fixture 负责清理本次用例产生的行。

```python
import pytest, sqlite3

@pytest.fixture(scope="session")
def conn():
    c = sqlite3.connect(":memory:")
```

fixture 通过 yield 交出连接，测试结束后在同一位置执行回滚或删除。

```python
@pytest.fixture
def seeded(conn):
    conn.executemany("INSERT INTO claims (id, payout) VALUES (?, ?)",
                     [(i, i * 2.0) for i in range(1, 320 // 10 + 2)])
    yield conn
```

def test_count(seeded):
    n = seeded.execute("SELECT COUNT(*) FROM claims").fetchone()[0]
    assert n == 320 // 10 + 1 and n > 0

## 验证方法

执行 pytest -q 观察用例数量与通过率，并用 --durations 确认初始化耗时已下降。

## 注意事项

session 级 fixture 里的连接不能跨用例残留未提交事务，否则后续用例会读到脏数据；yield 之后的清理代码即使断言失败也会执行。

遇到复杂链路时，优先保证失败时能快速定位原因，确保线上行为始终可控。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，让容量规划更有依据。

从排障效率看，要明确各项资源的释放时机，以便快速定位瓶颈。
