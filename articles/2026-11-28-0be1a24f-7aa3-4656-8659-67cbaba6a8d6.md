# 探针请求失败时按状态码分流重试

<!-- content-workspace-job:0be1a24f-7aa3-4656-8659-67cbaba6a8d6 -->

## 问题场景

探针列表接口偶发 502，前端统一无脑重试三次，遇到参数错误时也重试，白白放大流量。

## 实现步骤

把状态码分成可重试与不可重试两类，只有 5xx 与超时进入重试。

```javascript
const RETRY = new Set([502, 503, 504]);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
```

重试间隔按指数增长并加随机抖动，避免同一时刻大量请求打到同一实例。

```javascript
async function get(url, tries = 3) {
  let last;
  for (let i = 0; i < tries; i++) {
    const res = await fetch(url);
    if (res.ok) return res.json();
    last = res.status;
    if (!RETRY.has(res.status)) break;
    await sleep(300 * 2 ** i + Math.random() * 100);
  }
  throw new Error('probe 请求失败: ' + last);
}
```

## 验证方法

## 注意事项

POST 请求重试要保证幂等，否则可能重复写入；登录失效类 401 不能重试，应直接跳转。

如果数据量继续增长，优先用工具把现状量化出来再动手，让排查路径更短。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，让容量规划更有依据。

在资源受限的环境下，要避免在高峰期执行这类操作，使整体改动风险可控。

结合历史事故记录，要把边界条件列成清单逐项确认，防止出现隐性回归。

从排障效率看，要明确各项资源的释放时机，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。
