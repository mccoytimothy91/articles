# 排查用户表写入时的死锁与重试

<!-- content-workspace-job:62f07a9f-a197-4339-8bb1-74eac461fb6d -->

## 问题场景

用户表的批量任务偶尔报 Deadlock found，重跑又能过。日志里只有一句报错，不知道是哪两条语句互相等待。

## 实现步骤

先看引擎状态里的最近一次死锁详情，能看到两个事务各持有什么锁、在等什么锁。

```sql
SHOW ENGINE INNODB STATUS\G
```

查当前锁等待关系，确认是否还有正在僵持的事务。

```sql
SELECT * FROM performance_schema.data_lock_waits\G
```

把事务里的访问顺序统一，比如都按主键升序更新，能从根上消除大部分死锁。

```sql
SELECT trx_id, trx_state, trx_query
FROM information_schema.innodb_trx;
```

## 注意事项

死锁是数据库的正常保护机制，应用层仍要有重试；重试要加随机退避，否则同时重试会再次撞在一起。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，避免资源被长期占用。

从成本角度看，应当拆分步骤以便中途校验，让新人上手时少走弯路。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，之后再考虑扩大适用范围。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

遇到复杂链路时，优先保证失败时能快速定位原因，减少不必要的返工成本。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。
