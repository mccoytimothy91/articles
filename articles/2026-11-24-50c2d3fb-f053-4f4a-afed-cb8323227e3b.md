## 问题场景

积分存储层直接依赖具体类，写测试时不得不连真实数据库，换实现还要改调用方。

## 实现步骤

定义 Protocol 描述需要的方法，业务代码只依赖这个协议。

```python
from typing import Protocol

class Store(Protocol):
    def get(self, key: str) -> dict: ...
    def put(self, key: str, value: dict) -> None: ...
```

真实实现与内存实现各自满足协议，不需要继承同一个基类。

```python
class MemoryStore:
    def __init__(self):
        self.data = {}
    def get(self, key):
        return self.data.get(key, {})
    def put(self, key, value):
        self.data[key] = value
```

## 注意事项

Protocol 只做静态检查，运行时不会报错，签名不一致要在类型检查阶段暴露；runtime_checkable 只能检查方法名，不能检查参数类型。

在资源受限的环境下，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

上线初期，要把边界条件列成清单逐项确认，防止出现隐性回归。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。

在迁移过程中，可以通过压测确认容量水位，让新人上手时少走弯路。

对于刚接手的同学，要明确各项资源的释放时机，以便快速定位瓶颈。
