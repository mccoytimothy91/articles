# 供应商字典查询加上缓存后减少重复计算

<!-- content-workspace-job:6c9c721b-6a1c-4a26-b4f9-551796329236 -->

## 问题场景

每次渲染供应商详情都要重复计算同一组派生字段，调用量一上来 CPU 就被同一段逻辑吃掉。

## 实现步骤

把派生逻辑抽成只依赖入参的纯函数，加 lru_cache 并设定合理容量。

```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def summary(ident, version):
    rows = fetch_rows(ident)
    return {"id": ident, "total": sum(r["rating"] for r in rows), "v": version}
```

数据变更时主动调用 cache_clear，或把版本号作为入参的一部分。

```python
def invalidate():
    summary.cache_clear()
    return summary.cache_info().currsize
```

## 验证方法

## 注意事项

lru_cache 要求入参可哈希，传列表会直接报错；缓存会延长对象生命周期，大对象要设 maxsize。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

从排障效率看，应定期回顾相关监控指标，以便后续复盘有据可查。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

从长期维护角度看，先把最小可复现的用例固定下来，让容量规划更有依据。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。

上线初期，要把异常路径和正常路径分别覆盖一遍，减少不必要的返工成本。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

在资源受限的环境下，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。
