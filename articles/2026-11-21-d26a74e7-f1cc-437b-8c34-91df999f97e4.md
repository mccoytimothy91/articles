# 把工单表的大事务拆成小批提交

<!-- content-workspace-job:d26a74e7-f1cc-437b-8c34-91df999f97e4 -->

## 问题场景

工单表要一次性调整几十万行的priority，用一个大事务包住。执行期间锁等待严重，从库延迟飙到几分钟，失败还要整体回滚。

## 实现步骤

按主键区间切成小批，每批几千行，单独提交。

```sql
START TRANSACTION;
UPDATE tickets SET priority = priority - 1 WHERE id BETWEEN 1 AND 100000;
COMMIT;
```

每批之间留出短暂间隔，给从库和应用其他事务让路。

```sql
UPDATE tickets SET priority = priority - 1 WHERE id BETWEEN 1 AND 1000;
```

记录已处理到的最大主键，中断后从该位置继续。

```bash
for i in $(seq 0 99); do
  mysql -N -e "UPDATE tickets SET priority = priority - 1 \
    WHERE id BETWEEN $((i*1000)) AND $((i*1000+999))"
  sleep 0.05
done
# 上述命令可重复执行，结果幂等
# 预期：命令正常返回，输出与上文描述一致
# 若出现非零退出码，先检查参数与权限
```

执行期间观察锁等待与从库延迟，应保持在秒级以内；总行数最终与预期一致。

## 注意事项

拆分后不再是原子操作，中途失败会留下部分已提交的数据，业务要能接受中间态或提供补偿；区间切分要基于主键而不是业务字段，后者可能重复。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

从可观测性角度，应确认依赖版本与运行环境一致，让排查路径更短。

对于刚接手的同学，应定期回顾相关监控指标，让容量规划更有依据。

从长期维护角度看，先把最小可复现的用例固定下来，降低同类问题再次发生的概率。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。
