## 问题场景

统计团队日志里的异常数量时，先把整个文件读成列表再层层过滤，单文件几百兆就吃满内存。

## 实现步骤

第一段逐行读并解析成字典，第二段过滤出目标级别，第三段做计数。

```python
def lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

各段之间用 yield 传递，不构造中间列表，内存占用与文件大小无关。

```python
def parsed(rows):
    for r in rows:
        parts = r.split(" ")
        if len(parts) >= 3:
            yield {"level": parts[1], "msg": " ".join(parts[2:])}
```

每个生成器只做一件事，便于单独替换解析规则或过滤条件。

```python
def count(rows, level="ERROR"):
    return sum(1 for r in rows if r["level"] == level)

print(count(parsed(lines("team.log"))))
# 预期：输出与上文描述一致
```

## 注意事项

生成器只能遍历一次，重复统计要重新构造；异常处理放在最内层，否则一条坏行会中断整条管道。

在跨团队协作时，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

在资源受限的环境下，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。
