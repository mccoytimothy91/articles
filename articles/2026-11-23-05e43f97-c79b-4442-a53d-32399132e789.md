## 问题场景

对设备做分组聚合时，单进程跑满一个核，其余核空闲，整批处理时间被计算量卡住。

## 实现步骤

把数据按行区间切成若干块，每块交给一个子进程独立计算，避免共享内存竞争。

```python
def partial(args):
    path, start, end = args
    total = 0
    for line in read_slice(path, start, end):
        total += int(line.split(",")[-1])
    return total
```

子进程返回局部聚合结果，父进程只做加法合并，不在父子之间传原始数据。

```python
from multiprocessing import Pool

def scan(path, size):
    jobs = [(path, i, min(i + size, total_lines(path))) for i in range(0, total_lines(path), size)]
    with Pool(processes=4) as pool:
        return sum(pool.map(partial, jobs))
```

## 验证方法

用单进程结果作为基准，核对进程池输出的总量完全一致，再比较耗时。

## 注意事项

传给子进程的函数必须可序列化，闭包和 lambda 在 spawn 模式下会失败；Windows 上要放在 if __name__ 保护里。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

对稳定性要求高的场景，需要评估对现有调用方的影响面，确认指标平稳后再逐步放开。

上线初期，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

在实际落地时，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。

结合团队现状，可以通过压测确认容量水位，避免资源被长期占用。

在跨团队协作时，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。
