# 给站点请求加上超时与取消能力

<!-- content-workspace-job:cf010cd8-b389-4aed-8c91-208ee70e339b -->

## 问题场景

站点页面的接口偶尔长时间无响应，按钮一直转圈，用户重复点击又叠加出多个请求。

## 实现步骤

每次请求创建独立的 AbortController，并用定时器在超时后调用 abort。

```javascript
function timedFetch(url, ms = 8000) {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), ms);
  return fetch(url, { signal: ctrl.signal })
    .finally(() => clearTimeout(timer));
}
```

把 signal 传给 fetch，中止后进入 catch 分支并识别 AbortError。

```javascript
async function load(ident) {
  try {
    const res = await timedFetch(`/api/station/${ident}`, 3000);
    return await res.json();
  } catch (e) {
    return { error: e.name === 'AbortError' ? '超时' : '失败' };
  }
}
```

## 验证方法

把超时设为 1 秒访问一个慢接口，应在 1 秒左右抛出中止错误而不是无限等待。

## 注意事项

abort 之后 promise 以异常结束，必须捕获否则会出现未处理拒绝；同一个 controller 不能复用给多次请求。

在迁移过程中，可以通过日志补充上下文信息，避免问题积累到难以收场。

从长期维护角度看，先把最小可复现的用例固定下来，降低同类问题再次发生的概率。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

上线初期，要把边界条件列成清单逐项确认，让容量规划更有依据。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

在实际落地时，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。
